# DNS hosting (M3, dns stream) — design

Date: 2026-11-14. Status: implemented on branch `m3-dns`, from
`m2-integration` (43f8b69).

## Goal

The host is the authoritative DNS server for its customers' domains, as
established hosting panels provide it: the operator configures the host's
name servers once; a zone is created by itself for a customer's domain with
records pointing at this host; customers edit their zones; secondaries
replicate them; zones can be signed with DNSSEC. Everything follows the
engine's rules: records are the proof of ownership, files are rendered from
records, every change is validated by the server's own checker before it is
activated, `Reconcile` compares it all, suspension and deletion are decided,
and no secret is ever in an argument vector, a log, a record or a response.

## The DNS server: BIND, run by OxPanel

**Chosen: BIND 9.16 from AppStream** (`bind`, `bind-utils`; AlmaLinux 9
ships 9.16.23). Weighed against the alternatives:

- PowerDNS, NSD and Knot are only in EPEL. A third-party repository would
  become a dependency of the RPM and of every install from source, for a
  feature that must be in the first release. (Knot would have been the most
  pleasant to drive: `knotc` with zone-level transactions.)
- BIND covers everything the brief needs out of the box: authoritative-only
  operation, per-zone reload over its control channel (`rndc reload <zone>`),
  `reconfig` that loads new zones without touching the others, TSIG,
  NOTIFY, catalog zones (RFC 9432 schema 1, so plain secondaries learn new
  zones by themselves), response-rate limiting, and **fully automatic
  DNSSEC** (`dnssec-policy` with inline signing: key generation, signing,
  re-signing, NSEC3). Its checkers (`named-checkconf`, `named-checkzone`)
  are the validators the brief asks for.
- Its configuration language is the risk: everything rendered into it is
  built from allow-listed values (below), and every file is checked by
  BIND's own tools before BIND sees it.

**Own unit, own configuration, the distribution's untouched.** The brief
suggested one include in the distribution's main configuration, as
`nginx::ensure_include` does. That cannot work for BIND: the stock
`/etc/named.conf` listens on the loopback only and is a recursive resolver
for the host; serving the public authoritatively means changing its
`options` block (`listen-on`, `recursion`, `allow-query`, `version`,
`rate-limit`), and an `include` cannot change an `options` block. Instead
OxPanel runs BIND as its own service, `oxpanel-dns.service` (shipped in
`packaging/systemd`, enabled and started by the daemon once DNS hosting is
switched on), with a configuration it owns completely:

- `/etc/named/oxpanel/` (root:named 0750; labelled `named_conf_t` like the
  rest of `/etc/named`): `named.conf`, `zones.conf`, `rndc.conf`, and the
  keys `rndc.key` and `transfer.key` (root:named 0640, generated by the
  daemon from `/dev/urandom` on first use).
- `/var/lib/oxpanel-dns/` (root:named 0750; `named_cache_t` by a rule in
  `oxpanel.cil`, the type of the server's own writable directories):
  `zones/` (zone files, root 0644, and the server's signed copies and
  journals; 0770 root:named), `keys/<zone>/` (signing keys, named 0700),
  `data/` (the server's working directory), `staging/` (root 0700: zone
  files waiting for the checker).

`/etc/named.conf` and `named.service` are never touched. Running both
servers is a conflict (port 53, control port 953); `GetHostInfo` warns if
the stock one is active.

The unit starts named as root with `-u named` (BIND's own privilege drop,
as the packaged unit does; SELinux domain `named_t` by the packaged policy)
and adds what the packaged unit lacks: `ProtectSystem=strict` with only
`/var/lib/oxpanel-dns` writable, no homes, private `/tmp` and devices,
kernel protections, `MemoryDenyWriteExecute`, a capability bounding set of
exactly what BIND keeps after `-u`, and the `@system-service` system-call
filter. `ExecStartPre` runs `named-checkconf`.

**What the configuration enforces** (`dns::bind::render_named_conf`):
authoritative only — `recursion no`, `allow-recursion { none; }`,
`allow-query-cache { none; }` (no open resolver, also not for the host);
`allow-transfer { none; }` globally and `{ key "oxpanel-transfer"; }` per
zone; `allow-update { none; }`; `notify explicit` with `also-notify` to the
configured secondaries only, and `server` statements that sign NOTIFY and
transfers with the transfer key; `version none`, `hostname none`,
`server-id none`; response-rate limiting (20 responses/s per client and
answer, the host itself exempt); the control channel on 127.0.0.1:953 with
the root-only rndc key. The catalog zone is queryable and transferable with
the transfer key only (it lists every hosted domain).

**The daemon keeps `PrivateNetwork=yes`.** It validates with the checkers
(local files only) and starts/reloads the unit with `systemctl`. `rndc`
needs TCP on the loopback, so it runs in a transient unit (`systemd-run
--wait`, no capabilities, read-only system), its output written by systemd
to a root-only scratch file — the pattern `xfs_quota` already uses. No
`ReadWritePaths` change was needed (`/etc` and `/var/lib` were writable).

## Validate, activate, roll back

- **A zone change** (`dns::ops::apply_zone`): the zone record is saved
  first (with a new serial if the content changed), the zone is rendered to
  `staging/`, `named-checkzone -k fail -m fail -M fail -S fail -i local` runs
  on the staging copy; if it refuses, the previous record is restored, the
  live file was never touched and the checker's words are returned
  (`INVALID_ARGUMENT`). Otherwise the live file is replaced atomically and
  that zone alone is reloaded (`rndc reload <zone>`). `-m fail` is one step
  stricter than the server: an MX pointing at a name of the zone without an
  address is refused instead of loaded with a warning.
- **A change of the set of zones** (`dns::ops::apply_server`): `named.conf`,
  `zones.conf` and `rndc.conf` are rendered and written, `named-checkconf`
  runs, and if it refuses the previous files are restored. Then
  `systemctl reload oxpanel-dns` (`rndc reconfig`: new zones loaded, removed
  zones dropped, the others untouched) and `rndc reload` of the catalog.
- **Resumable.** Zone records carry a state (provisioning, ready, deleting)
  and the serial the server was last told to load; a repeated request, or
  the daemon's start-up convergence, finishes what an interrupted one began.
  If the server is not running, the engine starts it instead of reloading.

## Name servers and host settings

`OXPANEL_DNS=true` switches DNS hosting on; it then requires
`OXPANEL_DNS_NAMESERVERS` (in order; the first is the SOA's primary),
`OXPANEL_DNS_SOA_CONTACT` and `OXPANEL_DNS_IPV4` and/or `OXPANEL_DNS_IPV6`.
The addresses are **never guessed** from the interfaces — behind NAT those
are private — `--check-config` and start-up refuse an incomplete
configuration. Optional: `OXPANEL_DNS_SECONDARIES`, default and negative
TTL, per-tenant zone and per-zone record limits (50 / 500), the resolver the
outside checks ask, the public suffix list's path. All values are
allow-listed (host names as `Domain`, addresses parsed, the contact
`a-z 0-9 . _ -` before the `@`). `GetHostInfo.dns` reports all of it, the
server's installed version, whether it runs, and warnings.

**One server answering as ns1 and ns2.** Without a secondary, every
configured name must point at this host. It works — resolvers get answers —
but there is no redundancy: if the host is down, the domains do not resolve
at all, and registrars that check for two *different* servers may object.
It is allowed and flagged (`HostInfo.dns.warnings`); one configured name
server is flagged too (registrars require two).

## Secondaries

Standard NOTIFY + zone transfer, authenticated with TSIG (`hmac-sha256`,
key `oxpanel-transfer` in `/etc/named/oxpanel/transfer.key`, root:named
0640 — the server must read it; generated by the daemon, never in argv,
logs, records or responses). The operator copies that file to each
secondary. Secondaries do not need to be OxPanel hosts: OxPanel publishes a
**catalog zone** (`catalog.oxpanel.invalid`, RFC 9432 schema version 1 with
SHA-1 member labels, which BIND 9.11+ and Knot read, and PowerDNS 4.7+), so a
secondary configured once with the catalog picks up every zone that is
created or deleted; the handbook shows the secondary's configuration. A
secondary that cannot read catalogs gets the zone list from
`oxpanel-ctl dns zone-list`.

Proven for real: a second BIND instance configured exactly as the handbook
says (port 853 on the loopback, `dns_port_t` in the stock policy) learns
zones from the catalog, receives NOTIFY, transfers with TSIG, drops deleted
zones, serves signed zones; serials match. In the integration container and
on the enforcing VM.

## Zones: apex, ownership, overlap

**The apex is the registrable domain, from the host's public suffix
list.** `shop.example.co.uk` gets the zone `example.co.uk`. The list comes
from the AlmaLinux package `publicsuffix-list` (`/usr/share/publicsuffix/
public_suffix_list.dat`, kept current by the distribution; a `Recommends`
of the RPM), read and cached by mtime (`dns::psl`); the engine embeds no
copy of its own (the list is MPL-2.0, which `deny.toml` does not allow, and
a copy would age). Both sections count (ICANN and private: `user.github.io`
is registrable), Unicode rules are converted to A-labels with our own
RFC 3492 encoder. Without the file, DNS hosting is unavailable — never a
guess. An explicit `CreateDnsZone` may name any registrable domain or a
name below one (`shop.example.com` as a zone of its own), never a public
suffix.

**What stops tenant B from getting records in tenant A's zone:**

- A zone belongs to exactly one tenant, recorded; every zone request names
  the tenant and another tenant's zone is `NOT_FOUND`.
- Zones never overlap — no zone inside another, of any tenant (the same
  tenant adds records to its zone instead), so on this server a name is
  answered by exactly one zone and one owner.
- A zone cannot be created over a name that is a site of another tenant
  (first come, as server names of sites already are).
- No zone is ever a public suffix, so no tenant can answer, on this host,
  for everyone below `co.uk` or `github.io`.
- B's site *inside* A's zone (`blog.example.com` for B under A's
  `example.com`) is served, but gets no records from the engine — A decides
  what `blog.example.com` resolves to. `VirtualHost.dns_zone` is empty.

`shop.example.com` created before `example.com`: the zone is
`example.com` from the start (the registrable domain), so the later site
lands in the same zone. A site opts out with `dns_opt_out`
(`vhost set --no-dns`) when its domain's DNS is hosted elsewhere.

What this does not prove: that the customer owns the domain. As with every
shared host, the first tenant to claim a name holds it here; the zone only
matters publicly once the registry delegates the domain to these name
servers, which `CheckDnsZone` reports.

## Records

`AddDnsRecord`, `UpdateDnsRecord` (by id), `RemoveDnsRecord`, `GetDnsZone`,
`ResetDnsZone`. Types: A, AAAA, CNAME, MX, TXT, SRV, CAA, NS (delegation of
a name below the apex). Allow-list validation per field (`dns::rr`):

- **Names** relative to the zone (`@`, `www`, `_dmarc`, `s1._domainkey`,
  `*.dev`): labels of `a-z 0-9 - _`, 1–63 characters, not starting or
  ending with `-`; the whole name at most 253; `*` only as the whole
  leftmost label and only for A, AAAA, CNAME, MX, TXT; `_` not in owner
  names of A, AAAA, MX and NS (host names; the server refuses them); SRV
  names are `_service._proto…`; a fully-qualified name given where a
  relative one is meant (`www.example.com` inside `example.com`) is refused
  with the right spelling. Nothing that can escape the zone or carry syntax
  can pass.
- **Host-name values** (CNAME, NS, MX, SRV targets) absolute, ≥ 2 labels,
  not an address; `_` allowed in CNAME targets (providers' DKIM keys);
  `.` for a null MX (priority 0) and an SRV "no service".
- **Addresses** are parsed (`Ipv4Addr`/`Ipv6Addr`) and re-printed;
  unspecified, multicast and broadcast refused.
- **TXT**: printable ASCII only (no line break, tab, NUL or non-ASCII), up
  to 4000 characters, given as one value; the engine splits it into
  character-strings of at most 255 bytes, escapes `"` and `\`, and quotes
  each — `$INCLUDE`, `;`, `(` stay literal text. **CAA**: flags 0/128, tag
  issue/issuewild/iodef, value printable without `"`/`\`, iodef a
  `mailto:`/`https://` URL. **TTL** 0 (zone default) or 60 s – 1 week;
  numbers in their ranges.
- **Zone-level rules** (`dns::check_rules`): no CNAME at the apex; a CNAME
  is alone at its name; MX and SRV must not point at a CNAME of the zone
  (RFC 2181; the engine can only know its own zone); a null MX is the only
  MX; a delegated name carries only NS, and below it only address (glue)
  records; records of one name and type share a TTL; at most 500 records
  per zone, 50 zones per tenant (configurable).
- **Rendering** (`dns::zone`): one header comment, the SOA, apex NS, the
  sites' address records, (mail hook), then the tenant's records — one line
  each, every owner fully qualified, no `$` directive at all. Property tests
  feed arbitrary text into every field and require every accepted record to
  render as exactly one well-formed line inside the zone, every TXT to give
  back its value, and every zone file to hold exactly the lines its records
  ask for.

**Protected and editable.** The engine maintains, and the API shows as
`protected` (id 0, origin `zone` or `site:<domain>`): the SOA (from the host
settings and the serial), the apex NS records (the configured name
servers) and the A/AAAA records of every name of every site of the zone's
tenant (domain and aliases). The tenant cannot add A, AAAA or CNAME at a
site's name, NS at the apex or at/above a site's name, or anything at the
apex that conflicts. To point a site's name elsewhere (a CDN), the site
opts out of DNS hosting or drops the name. When a site *claims* a name that
already has the tenant's A/AAAA/CNAME records (an alias added later), the
site's records replace them (logged): adding the alias asked for exactly
that. A name the tenant delegated with NS is left to the delegation, even
if a site claims it. **Reset to defaults** (`ResetDnsZone`) removes every
record the tenant added; the protected ones stay.

**Default records** are the protected ones: SOA, NS, and A/AAAA for the
site's names — "apex and www" when the site has `www` as an alias, which is
how sites are created. Deliberately no address records for names no site
serves (they would reach the catch-all, which closes the connection, and
fail Automatic HTTPS). **No CAA by default**: the host's ACME authority is
configurable (Let's Encrypt, ZeroSSL, Google, a private CA) and uploaded
certificates come from anywhere; a default CAA naming one would break the
others. Tenants may add CAA. **No mail records by default** (no mail server
on the host): `dns::zone::mail_records` is the hook where engine-maintained
MX/SPF/DKIM/DMARC go when OxPanel hosts mail (protected, rendered between
the sites' and the tenant's records). Tenants who use an external provider
add its MX/TXT/CNAME/SRV records; the handbook has a worked example.

**Serials** (`zone::next_serial`): the current time in seconds when that is
later than the previous serial in RFC 1982 arithmetic, otherwise previous
+ 1. A new serial is issued exactly when the rendered content (hash in the
record) changes. It survives restarts (in the record), a clock stepping
back (counts up), and only ever moves forward, which is what secondaries
need. A signed zone is served with BIND's own serial (≥ the raw one);
switching signing on or off issues a serial above anything served.

**Sites and zones.** `ConfigureVirtualHost` and `RemoveVirtualHost` call
`dns::site_changed` (best effort: the site is served whatever DNS does; a
failure is logged and shows in `Reconcile`). A new name not in any zone gets
an *automatic* zone for its registrable domain; every zone of the tenant
holding an old or new name of the site is re-rendered; an automatic zone
that no site uses any more and that holds no record of the tenant is
deleted. **A zone with the tenant's records outlives its last site**
(the tenant's MX and TXT keep working) until `DeleteDnsZone`. Zones created
with `CreateDnsZone` are never deleted by the engine. At start-up the daemon
converges: interrupted zone work is finished, sites without a zone (DNS
hosting just switched on) get one, every zone and the server configuration
are re-rendered (a changed address or name server reaches every zone).

## DNSSEC

`SetDnssec` / `oxpanel-ctl dns dnssec <zone> on|off`, per zone.

- **Signing is BIND's** `dnssec-policy` with inline signing: OxPanel
  writes the unsigned zone as always; BIND generates the key, signs, keeps
  the signatures fresh (re-signing before they expire, and on every change
  of the raw zone), and serves the signed zone to clients and secondaries.
  No signing code of ours.
- **Algorithm and policy** (`dnssec-policy "oxpanel"`): one combined
  signing key (CSK), ECDSA P-256 / SHA-256 (algorithm 13, small signatures,
  universally validated), lifetime unlimited. **Rollover:** none
  automatically — the key stays until the zone is unsigned, so the DS at
  the registrar never has to change. That is BIND's own default policy's
  choice too; scheduled rollovers would need the registrar's DS to change
  each time (no CDS/CDNSKEY automation with registrars exists for most
  TLDs). A key compromise is handled by switching off (after removing the
  DS) and on again, with the new DS at the registrar. Where it would go:
  `keys { ksk lifetime …; zsk lifetime 90d; }` gives automatic ZSK
  rollovers that need no registrar action; the policy is one function.
- **NSEC3**, no salt, no extra iterations, no opt-out (RFC 9276's advice):
  chosen over NSEC so that a zone's names cannot be listed by walking it —
  customers' unpublished subdomains stay unlisted to casual walking (NSEC3
  only raises the cost: offline dictionary attacks remain possible).
- **Keys** live in `/var/lib/oxpanel-dns/keys/<zone>/`, owned by the
  server's account, private halves mode 0600 (BIND writes them); the daemon
  never opens a private key. It reads the public `.key` file, computes the
  DS (SHA-256) and key tag itself (`dns::dnssec`, cross-checked against
  `dnssec-dsfromkey`), and `GetDnsZone` returns the **DS and DNSKEY
  records** for the registrar, the state (off / signing / signed), the
  algorithm and NSEC3. Tenants cannot read the keys (the directory tree is
  closed to everyone but root and named).
- **Switching off safely.** A zone whose DS is still published at the
  parent must not go unsigned (validating resolvers would answer SERVFAIL
  for the whole domain). Before switching off, the probe asks the
  resolver for the zone's DS: **published → refused**, with the correct
  order (remove the DS at the registrar, wait until it has expired from
  caches — its TTL, usually one or two days — then switch off); **cannot be
  checked → refused unless `force`**; none → the zone is written with a
  serial above the signed one served, the configuration drops the policy
  (reconfig reloads it unsigned), and the keys and signed copies are
  removed. Switching on writes a new serial too, so secondaries take the
  signed zone. `CheckDnsZone` reports the DS at the parent and whether it
  matches the zone's key.
- **Secondaries** transfer the signed zone (signatures included); proven
  with the TSIG secondary.

## Looking from outside: the probe

The daemon has no network. Three things need it: whether a domain is
delegated to the configured name servers, whether its parent publishes a
DS, and which serial each name server serves. `oxpanel-daemon dns-probe`
(the daemon's own binary in probe mode, ~300 lines with `dns::wire`, no new
dependencies) runs in a transient unit with `DynamicUser=yes`, no
capabilities, `NoNewPrivileges`, read-only system, only `AF_INET/AF_INET6`;
it sends plain queries (UDP, TCP when truncated) and writes one line per
question to a root-only file systemd opens. The parser is bounds-checked,
allows only backward compression pointers and is property-tested against
arbitrary bytes.

**Delegation** asks the resolver (`OXPANEL_DNS_CHECK_RESOLVER`, default
the host's first `nameserver`) for the zone's NS set: exactly the configured
servers → delegated; some → partial; others → elsewhere; NXDOMAIN → not
found; no answer → unknown; each with plain-language guidance. It asks a
resolver rather than walking from the root: the answer is what the world's
resolvers see. Nothing in the engine assumes a local zone is publicly
authoritative: Automatic HTTPS pre-checks names through the ACME client's
own resolution, exactly as before.

## Suspension, deletion, backups

- **Suspension** keeps every zone of the tenant answering, unchanged: mail
  and third-party services depend on the domain's DNS, and the site
  records still lead to the 503 pages. Changing a suspended tenant's zones
  is refused (`FAILED_PRECONDITION`); engine-driven updates (a removed
  site) still happen. To take a domain off the air (abuse), delete the zone.
- **Deleting a tenant** is refused while it owns zones (as for sites and
  databases). `dns::remove_tenant_zones(ctx, tenant)` removes them in order
  (server configuration first, then files and record) for the cascading
  delete on a sibling branch; the caller holds the mutation lock.
- **Backups**: zone data is engine records (`/var/lib/oxpanel/dns-zones`),
  not tenant files; backups do not include it (not built into backups, as
  asked). It is preserved by backing up `/var/lib/oxpanel` with the rest of
  the engine's state; signing keys (`/var/lib/oxpanel-dns/keys`) belong to
  the same host backup — a restored signed zone without its keys gets new
  ones, i.e. a new DS at the registrar. Said so in the handbook.

## Reconcile

`DNS_ZONE_DRIFT` (zone file missing or not what the records render — hand
edit, or sites/settings changed since; interrupted creation or deletion;
the server not serving the zone at the recorded serial; a zone of a tenant
that no longer exists), `ORPHAN_DNS_FILE` (a file in the zones directory or
a key directory no zone accounts for), `DNS_SERVER_DRIFT` (server
configuration differs or is missing, a key missing, unusable or readable by
others, the server not running, zones existing while DNS hosting is not
available), `DNS_SECONDARY_DRIFT` (a secondary serving another serial or
not the zone at all), `DNSSEC_DRIFT` (a signed zone without a key-signing
key, keys left for an unsigned zone). Serials are asked through the probe
(one transient unit per reconcile when zones exist).

## API, CLI, scopes

RPCs at the end of the service: `CreateDnsZone`, `ListDnsZones`,
`GetDnsZone`, `DeleteDnsZone`, `AddDnsRecord`, `UpdateDnsRecord`,
`RemoveDnsRecord`, `ResetDnsZone`, `CheckDnsZone`, `SetDnssec`. Scopes as
for databases (a customer manages its own zones): reads `read`, everything
else `vhost`. New fields after the highest numbers in use:
`VirtualHost.dns_opt_out = 12`, `dns_zone = 13`;
`ConfigureVirtualHostRequest.dns_opt_out = 10`; `HostInfo.dns = 35`;
`DriftKind` 30–34. CLI: `oxpanel-ctl dns zone-create|zone-list|zone-show|
zone-delete|zone-reset|zone-check|record-add|record-update|record-remove|
dnssec`, `vhost set --no-dns`, a `dns=` line in `host info`.

## Not included

DNSSEC key rollovers (the key is kept; see above) and CDS/CDNSKEY;
dynamic updates (RFC 2136); wildcard policy beyond "leftmost `*` for A,
AAAA, CNAME, MX, TXT"; geo or weighted answers; a registrar integration
(registering domains, setting name servers or DS automatically); reverse
(PTR) zones; mail records by default (the hook is there); ALIAS/ANAME at
the apex; per-record comments; zone import/export (AXFR from elsewhere,
zone-file upload); DNS over TLS/HTTPS; a UI; a firewall rule (port 53 TCP
and UDP must be opened by the operator); IPv6-only checks of secondaries
reached over IPv6 are as configured (no address-family fallback);
verification that the customer owns the domain beyond the delegation
check.
